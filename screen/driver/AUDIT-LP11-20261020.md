# LP-11、背光包发送阶段与实际回读

## 视频先启动与跳过 EF 的独立对照

2026-10-20，在 CAM/DISP0 测试普通显示模式（backlight_only=0）：

1. 保留 EF；prepare 跳过 29，保留 11 后 250 ms 等待。视频启动后静置 120 ms，
   发 29 后等 150 ms，再发 53=24，等 50 ms 才回读。
2. 仅将 skip_ef 改为1，经实际复位重新初始化，保持上述时序。

两组均读到 ID=93 65 04、0A=18、54=24、52=80 00、C7=00、05=00、0E=00、0F=C0，
主机 ERR0/ERR1=0；未观察到 Display On 状态位改变。05=00不等于已经证明所有扩展长包正确写入，
0E的瞬时值也不能单独证明 HS 视频始终没有同步。现场 PWM/画面变化仍待用户确认。
EF 之前立即回读 BA/C7 的旧实验也为00，因此不能把零值完全归因于 EF。

新增 video_before_on（当前实验默认1）、skip_ef（默认0）参数，便于分别复现；
诊断增加05/0E/0F，视频启动后静置期间不插入 BTA。
已将运行时 skip_ef 恢复0并重新初始化，保留视频先启动模式静态输出；没有启动循环或修改开机配置。
内核编译退出码0。远端日志 dmesg-video-before-on-ef.log、dmesg-video-before-on-no-ef.log。
最初桌面占用时 FB blank/unblank 没有触发面板重初始化，已停止 display-manager，
以实际新增复位日志和 skip_ef=1 日志确认第二组有效，未把无新日志的操作算入结果。

本地 RP1 源码的 rp1dsi_dsi_send 在发送前后均等待两个 FIFO 清空（低四位为5），
与外部审计所引“只等 FIFO 非满”的片段不同。等待超时后没有返回错误仍值得后续检查，
但当前没有证据证明这里发生了 payload FIFO 溢出。

本记录更新此前“主机先初始化就能保证 LP-11”的不完整表述，保留失败和成功的实机对照。
分支：`codex/fl7707-lp11-rx`。仅 CAM/DISP0 运行时加载，启动配置未改动。

## 关键修正及结果

prepare_prev_first 只改变 panel/bridge 的调用顺序，不配置时钟线模式。
RP1 源码根据 MIPI_DSI_CLOCK_NON_CONTINUOUS 决定 LPCLK_CTRL 是 1 还是 3。
加入该 flag 后 flags 从 0x805 变成 0xc05。

| 项目 | 原状态 | 非连续时钟修正后 |
| --- | --- | --- |
| LPCLK_CTRL | 1 | 3 |
| PHY_STATUS（复位释放前后） | 早先运行时采样 1529 | 15bd |
| CLK Stop 位 bit2 | 早先采样为 0 | 复位前后为 1 |
| 初始化前 0A | -5，无有效数据 | ret=1，08 |
| 初始化后 04 | -5，无有效数据 | ret=3，93 65 04 |
| 初始化后 0A | -5，无有效数据 | ret=1，18 |
| ERR0/ERR1 | 首次采样 0/2 | 各次成功读取阶段均 0/0 |

旧 PHY_STATUS 采样发生在视频运行时，不能单凭它重建旧版本整个复位期间的状态；
新版本已在 prepare 中分别采样复位前、释放后及各读请求后。

DSI INT_ST1 bit1 的 LP 接收超时含义用同类 Synopsys 控制器的 ST 官方 CMSIS 定义交叉核对。
实际成功回读表明，不必补主机接收寄存器也能建立基本通信；这不等于所有主机配置在所有面板上都最优。

## 对接收配置审查意见的验证

实机控制器 VERSION=3133312a（Synopsys 1.31），修正时钟后仍保持：

- PCKHDL_CFG=5，BTA 与 EoTp TX 开启，RX ECC/CRC 未额外启用。
- PHY_TMR_RD_CFG=0。
- PHY_IF_CFG=1，2 lanes，STOP_WAIT 字段未额外写入。

以上状态下 0A、04 等已正常应答。因此本次未启用 MAX_RD_TIME=10000、接收 ECC/CRC、
STOP_WAIT=0x20 的补丁，也没有保留该试验补丁的写寄存器路径。
先前“BTA 已开启”不足以排除时钟配置问题，之前的通信失败并非已经证明的屏幕硬件故障。

## 背光命令发送阶段及亮度顺序

上版 enable 重发 C7 扩展长包会占用视频模式的 LP 命令窗口，且发生在厂家 EF 之后。
现改为 C7.PWM_OE 在原表对应位置打开，仍在 Command Mode 中；
视频阶段只用 53 的短包开关背光，不再重发 C7。

另外，亮度写入顺序存在实测差异：

| 顺序 | 54 控制回读 | 52 亮度回读 |
| --- | --- | --- |
| BCTRL 复位关闭时写 51，然后才 53=24 | 24 | 00 00 |
| 先 53=20，写 51，再在视频稳定后 53=24 | 24 | 80 00 |

先用 53=20 允许亮度控制、保持 BL 关闭，视频启动 50 ms 后再置 BL=1。
51 的单参数和双参数都做了相同顺序下的对照：均读到 80 00，不能声称单参数写法是本次点亮修复。
默认仍采用厂家手册画出的双参数；可用 brightness_bytes=1/2 重复该对照。
52 请求两字节时 RP1 返回的是 FIFO 读取长度，不能仅凭第二字节为零推断面板物理响应包有两字节。

## 黑屏仍存在时的证据

用户确认通信恢复后仍无画面、背光。

- 0A=18，按所供 FL7707N 手册解释为 Sleep Out/Normal，但 Display On 与 Booster 状态位仍为 0。
- 54=24、52=80 00，已有标准控制及亮度命令写入的证据。
- 在原表 BA/C7 写入后立即读：BA 写首参31、读00；C7 写首参90、读00。
  在 EF 之后再读 C7 也为00。扩展寄存器 DCS/Generic 读取都试过，但零值本身不能证明它们一定可按此方式回读。
- 0C 读到70，与 FL7707N 文档的 RGB888 默认值相符。
- DA/DB/DC 分别读93/65/04，与04结果一致。这个 ID 也见于 JD9365 系列实测记录，
  但 ID 可由模组定义，且0C行为与所供资料相符，不能仅凭 ID 就换另一套屏幕的电源/GIP参数。

曾在无其他发送进程时，用已确认地址 1f0011c000 的 /dev/mem 映射发送同一 B9 解锁值的
Generic 长包作窄范围对照；视频模式下出现 CMD_STATUS=11 的 payload FIFO 等待。
已用正常 FB 关闭/恢复重置主机，恢复有效回读。该试验不构成完整 Command Mode 下 Generic 初始化的验证。
该等待也支持把扩展长包留在 Command Mode 的保守实现。

随后完整厂家表在 Command Mode 下另作 Generic/DCS 对照：
vendor_generic=1 将 B0 以上扩展命令换成 Generic 包，标准 11/29/51/53 保持 DCS；
BA/C7 同样读00，04/0A/54/52与DCS实验相同，未观察到这一包类型变更修复寄存器反馈。
已恢复 vendor_generic=0，保留开关用于复现，不将 Generic 认定为当前正确包类型。

## 万用表测量模式

meter_reset_ms=0：正常复位；1～30000：启用延长的低/高/低三个阶段。
仅针对已识别的 raspberrypi,rp1dsi 主机映射寄存器。

测量时保存 LPCLK_CTRL，写0撤销 HS 时钟请求，等待 PHY_STATUS 的 CLK/D0/D1 Stop 位全部为1；
此时不发送命令，RST 低、高、再低各保持指定时间。最后正常释放复位、发送初始化，再恢复原时钟模式。
初始化错误时也恢复保存的时钟配置并保持复位。

已在设备开启 meter_reset_ms=30000 的后台循环，实际日志确认 CLK/D0/D1 Stop 全部进入，
PHY=15bd，并依次出现 RST 低30000ms、高30000ms。系统欠压标志为0。
该模式不会修改冷启动配置，断电后停止。后台循环每轮90秒保持阶段后会有短暂正常初始化及视频阶段。

预期测量：数据/时钟 LP-11 两线分别对 GND 约1.2V；U6 输出侧 RST 低约0V、高约1.8V。
这些是预期值，实际引脚电压仍需用户测量，控制器 Stop 位不能代替万用表读数。

用户随后在屏幕旁 FPC 延长模块实测：CLK+/CLK-/D0+/D0-均约1.22V，
U6输出RST约1.88V、远端RST约1.74V，确认有周期性切换。
因此 LP-11 和复位切换已得到该测点的电压证据；尚未直接量到芯片焊盘。
按IOVCC=1.88V、VIH最低0.7×IOVCC计算为1.316V，远端1.74V满足高电平要求。
两处RST差约0.14V应使用同一近端GND复核，当前不将其单独认定为故障。
测量完成后已将meter_reset_ms设回0并停止慢速后台循环。
当前测量中的prepare执行完毕后，循环进程已退出；随后正常读回ID、54=24、52=80 00。
视频保持期间另用对齐的32位MMIO访问重发一次DCS Display On，再读0A仍为18，ERR0/ERR1为0。
该对照没有使Display On状态位改变；后续不应把芯片仍黑屏描述成基本通信再次失败。

## 验证及日志

### Display Off 下的独立背光试验

按用户要求增加backlight_only开关，默认关闭，实机以backlight_only=1加载。
保持Sleep Out，不发送29；另外明确发送28 Display Off，55=00关闭内容自适应调光。
为对照公开手册与厂家长参数差异，仅该模式将C7/C8各限制为两个参数，
写C7 90 00、C8 00 03，其余厂家参数不变，普通模式仍使用完整原表。
之后53=20、51=80 80；视频稳定后53=24。

编译退出码0，实机确认该路径运行：ID=93 65 04，0A=18，54=24，52=80 00，C7=00，主机ERR0/ERR1=0。
该实验读回标准背光/亮度配置成功，但尚未验证C7使能生效，也不能据此声称PWM引脚已经输出。
手册分别描述29的显示输出控制与C7/51/53的PWM控制，没有明确规定必须Display On才能产生PWM；
寄存器可在Sleep In访问不等于所有电源/时钟状态下引脚必然输出。本轮保留Sleep Out避免这一混淆。
现场PWM波形与背光变化待用户确认，当前测试静态保持，无慢速复位循环。

远端日志：`~/screen-bringup/dmesg-pwm-only.log`、`driver/build-pwm-only.log`。

现场后续反馈：独立模式仍无PWM、无背光，LED_A约5V。
进一步只读检查：0F=C0、0E=00、54=24、52=80、56=00、C7=00、C8首参=00，主机ERR0/ERR1均0。
按手册第50～51页，Sleep Out自检成功时会翻转0F的bit7/bit6；本轮从硬复位默认0开始，一次Sleep Out后C0
与通过寄存器装载和功能检查的结果相符，不能以“芯片不工作”概括现象，也不能代替外部电压实测。

找到RT-Thread官方FL7707N驱动使用dsi_eot_transmission_disable，做了NO_EOT_PACKET单项对照：
RXCFG从5变4，标准回读仍成功，但C7回读未改变。当前保留该兼容配置，未声称它已经解决PWM。
源码：https://raw.githubusercontent.com/RT-Thread-Studio/sdk-bsp-gd32h77d-realthread-ginopi/main/libraries/Board_Drivers/drv_lcd.c

随后仅独立背光模式，在Sleep Out的250ms等待结束后再次发送B9解锁，以及厂家完整长度的C7/C8
（仅同样调整PWM_OE和分频），仍在Command Mode执行。C7回读仍00；这不是已经证明的OTP覆盖修复。
该步骤不改GIP或电源寄存器，也不对另一型号屏幕的初始化表作替换。

最后一次性用单参数51 FF将亮度置满，读52=FF、54=24、0A=18，主机错误状态均0。
目的是让可能的100% PWM表现为直流高电平，方便万用表检查，不把“没有方波”误作没有使能。
实际PWM/EN电压与LED_A变化等待用户回报。重新初始化会恢复80。

远端补充日志：pwm-only-status.txt、dmesg-pwm-no-eot.log、dmesg-pwm-after-sleep.log、pwm-full-brightness.txt。

所有改动在设备内核6.18.50+rpt-rpi-2712编译，make退出码0；多次FB启停后的ID及状态回读可重复。
新版时钟及诊断过程中未修改内核模块安装位置或启动配置。
多次动态卸载产生的 DRM interface type ID ret=-28 告警仍有出现，但后续命令和FB均运行；
首次通信恢复时已存在此告警，不能把它与先前接收失败混为一谈。
