# JD9365 分页识别及最小启动实测

## 内置图案与实际像素内容对照

用户实测LED_A在满亮与80亮度间约12.4→11.5V，示波器未发现与画面明暗同步的变化；
约100us量级波动只作现场观察记录，不能未经频谱/频率测量就认定为开关频率或异常。
用户近看子像素（尤其绿色部分）感觉是显示内容在变，因此将重点转向内置测试、扫描和像素链路。

JD页1的4A读到80：按手册第69页，自动测试位为1、TEST_PAT_EN为0。
这不足以认定当时正在输出老化图案，仍需要显式关闭并用已知帧验证。
新增jd9365-diag.py --disable-test-pattern，将4A与~C0后写回并读回。

执行前SSH断开，用户随后确认误碰断电；等待20秒后重连，uptime约1分钟，
无运行时overlay，已恢复JD两通道、720行、外部电源02配置。
这次断连不作为驱动异常重启证据。

实机顺序：先show-pattern.py --fb 0 --pattern quadrants，再关闭软件测试位。
4A确实由80读回00，0A=1C、52=80、54=24，主机ERR0/ERR1=0。
当前帧为静态两黑两白四分块，保持不变，等待现场确认图案及闪烁情况。
没有修改VCOM、Gamma或GIP，没有修改开机配置。
远端快照：~/screen-bringup/jd9365-pattern-off.json。

## 720行及外部电源模式后的现场画面

用户确认jd9365_tcon_720=1、jd9365_power_nt=1之后出现彩条，但明暗交替闪烁、整体偏暗、
部分条带颜色不纯。照片中尚未看到帧缓冲预期的黑底数字0，不能把“出现条纹”当成像素内容已正确显示。
实际读取/dev/fb0的若干像素与黑底数字0测试帧一致；主机VID_MODE_CFG=BF00，未打开DSI主机内建图案位。

单项把标准51设为FF后读52=FF、54=24、0A=1C，主机ERR0/ERR1=0。
用户反馈变为只有背光，而且纯背光也有点闪烁。此时不能把闪烁完全归到视频数据上，
也不能把软件FF等同于引脚实际100%稳定使能。
已恢复51=80并重写彩条，现场恢复情况及PWM频率/幅度、LED_A波动待用户测量。
树莓派读到throttled=0，PMIC EXT5V约5.099V；单次读数不能排除板端供电动态问题。

直接MMIO的第一次临时诊断误将GEN_HDR与GEN_PLD_DATA地址交换，造成PKT=11等待超时；
通过正常FB powerdown/unblank重置主机后，PKT恢复15，正确地址写51及读52成功。
该超时属于诊断操作错误，不计入面板或主机故障证据。
现将已核对的常量GEN_HDR=6C、GEN_PLD_DATA=70封装在jd9365-diag.py中；
采用对齐32位访问、型号验证、只读状态及有范围限制的标准亮度设置，避免再次手工拼接地址。
仅在没有其他DSI发送任务时使用，会切页并在结束恢复页0；状态采样会读取并清除主机错误锁存。

```sh
sudo python3 jd9365-diag.py
sudo python3 jd9365-diag.py --brightness 0x80
sudo python3 show-pattern.py --fb 0 --pattern quadrants
```

show-pattern.py增加单路及静态纯色/黑白四分块选项，默认仍为双路彩条；
目前设备保持80和彩条，未在等待反馈期间自行切换其他图案。
诊断脚本的满亮快照保存在远端jd9365-full-brightness-snapshot.json：
页1 40/41=04/5A、55=02，页3 PWM=1A/00/01/06/80；页1 4A=80，TEST_PAT_EN为0。

分支：codex/jd9365-identify，起点03abf5d。仅CAM/DISP0运行时测试，未修改开机配置。

## 识别结果

用户补充商品详情标注JD9365S，随货资料却是FL7707N。
标准04/DA/DB/DC的93 65 04只能作为线索，因为这类ID可由模组定义。
本轮改为硬件复位后、发送任何FL表之前，用JD专用分页及内部型号寄存器识别：

1. E0 00；E1 93；E2 65；E3 F8，均为单参数DCS短包。
2. 连续选择页0、1、0、1、0，每页分别读取E0、8D、8E、8F和80。

| 页 | E0回读 | 8D | 8E | 8F | 80 |
| --- | --- | --- | --- | --- | --- |
| 0 | 00 | 00 | 00 | 00 | 03 |
| 1 | 01 | 93 | 65 | 0E | 62 |
| 0 | 00 | 00 | 00 | 00 | 03 |
| 1 | 01 | 93 | 65 | 0E | 62 |
| 0 | 00 | 00 | 00 | 00 | 03 |

全部ret=1。Jadard User Guide第81页定义页1的8D/8E为内部型号93/65，8F为芯片版本。
该分页相关性及内部型号匹配，确认本屏使用JD9365系列寄存器接口；
0E是内部版本值，与标准04中的第三字节04不同，不能据此单独判定S/DA的具体订货后缀。
页0的80=03按Espressif驱动定义为4-lane。此前FL的BA=31未把该屏切换到2-lane。

这也解释了为什么标准DCS读写工作、FL扩展BA/C7回读一直为00；
旧记录里按FL手册解释的扩展寄存器和PWM设置不再适用于本屏。

## 最小JD启动

jd9365_probe=1：只执行分页识别，结束RST保持低，enable不发显示/背光命令。
jd9365_probe=1 jd9365_start=1：识别通过后，保持JD解锁及页0，发送：

- 80=01，两通道。
- 3A=77，RGB888。
- 53=20、55=00、51=80，标准亮度配置。
- 11 Sleep Out后等待250ms。
- RP1启动视频后等待120ms，发29，等待150ms，再发53=24，等待50ms回读。

没有导入其他尺寸面板的模拟电源、Gamma或GIP表，没有写OTP控制寄存器。

实测80读回01，Sleep Out后0A=18；视频及29之后0A首次变为1C，Display On位已置位，
Booster位仍为0。54=24、52=80、05=00、0E=00、0F=C0，主机ERR0/ERR1=0。
这证明JD接口设置及显示状态发生变化，不能替代实际画面/PWM验证。
现场反馈待用户确认，当前保持这组配置，不运行循环。

硬复位后只读的页3默认PWM寄存器：98=1A、99=00、9A=01、9B=06、9C=80。
JD的PWM控制位在页3，不能沿用FL的C7/C8解释或分频公式。

## 复现与验证

```sh
make -j4
sudo insmod ./panel-fl7707n.ko jd9365_probe=1 jd9365_start=1
sudo dtoverlay -d . fl7707n-cam0
```

模块/overlay文件名暂时沿用历史名字，不代表当前走FL初始化；以参数和实际日志为准。
识别逻辑检查E0页号及内部型号93/65，不匹配则保持复位并返回错误。
启动参数应在加载模块时给出，识别与启动参数均只读，避免运行时切换损坏状态。

设备内核6.18.50+rpt-rpi-2712，实验版本编译退出码0。
远端日志：~/screen-bringup/dmesg-jd-identify.log、dmesg-jd-minimal.log。
热加载仍可能出现DRM interface type ID ret=-28，后续分页及状态读取均成功；
该告警与面板的内部型号及lane配置不应混淆。
